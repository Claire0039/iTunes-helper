# 把网易云 NCM 转换功能接入 iTunes 助手

> 结论：已经接进去了。产物是 **`iTunes助手.NCM版.exe`** —— 把网易云下载的 `.ncm` 文件
> 丢进「源文件夹」（或者**直接拖进窗口**），点「开始整理」，它会自动解密成 MP3/FLAC、
> 写入标签和封面，再走原有的命名模板 / 按日期归档 / 去重 / 生成 m3u8 播放列表流程。

### 4. 把文件直接拖进窗口

拖进来的音频文件（含 `.ncm`）会：

1. 把源目录设为这些文件所在目录；
2. 设置一个「**只处理这些文件**」的开关 —— 不会顺手把整个文件夹几百首歌都扫进来；
3. 自动执行一次扫描，**追加到现有列表后面**（原有歌曲不会被清空）。

> **追加而不是替换**：`core.scan_folder` 在拖入分支里会把新扫到的曲目和
> `model._jobs` 里已有的曲目合并（按绝对路径去重）再返回给 Worker，
> 所以列表是「原有 + 新增」，同一个文件重复拖也不会出现两行。
> 原有那一行会保留在原来的位置，它的状态不会因为新拖入而被顶掉。

> **必须同时接管 `dragMoveEvent`**：Qt 在拖动过程中会持续派发 `dragMoveEvent`，
> **只要它没被 accept，光标就变成禁止符号，松手时压根不会派发 `dropEvent`** ——
> 用户看到的现象就是「拖进去完全没反应」。原程序只覆盖了 `dragEnterEvent`，
> 所以这里补上了 `dragMoveEvent`。不支持的格式（例如 `.txt`）会被拒绝，
> 光标正确显示为禁止；文件夹仍然接受，走原来的整目录扫描。

拖**文件夹**仍然走原来的逻辑（重新扫描该目录）。手动改源目录或点「浏览」会取消这个开关。

#### 音频后端说明（为什么不是 QtMultimedia）

这个程序打包时只带了 QtCore / QtGui / QtNetwork / QtSvg / QtWidgets，
**没有 QtMultimedia**，也没法补装。所以播放用的是 Windows 自带的
**MCI**（`winmm.dll`，通过 ctypes 调用），零依赖，底层走 DirectShow /
Media Foundation，MP3 / WMA / WAV 开箱即用。

> **一个真实的坑**：MCI 的 MP3 解析器打不开带「大 ID3v2 标签」的文件 ——
> 典型就是网易云下载的歌内嵌了 1~2 MB 封面，会直接报「初始化 MCI 时发生问题」。
> 处理办法是：直接打开失败时，把 MPEG 音频帧抽出来写成一个临时副本再播放，
> **原文件绝不被修改**，副本按 (路径, 大小, mtime) 缓存复用。
> 实测 15 MB / 1.1 MB 标签的文件：抽取 92 ms，打开 229 ms，之后跳转精确到毫秒。

### 5. 顺手修掉的两个原版问题

| 问题 | 现象 | 修法 |
|---|---|---|
| **扫描后界面永久卡在忙碌态** | `Worker` 是 `QObject` 且自带 `finished` 信号，但 `do_scan` **只 emit preview、从不 emit finished**（只有 `do_run` 会）。于是 `_running` 一直是 True，点过一次「扫描预览」后两个按钮就再也点不动了 | `do_scan` 结束时置标志位，主线程看门狗发现后调用 `_teardown_worker()` 收尾 |
| **Windows 深色模式下界面花色** | QSS 里写着 `QWidget#Root { background: … }`，但**没有任何控件叫 Root**（这条规则是死代码）；标题栏是自定义控件又没打开 `WA_StyledBackground`。结果窗口底色和标题栏**跟随 Windows 深浅色模式**，其余控件却由 QSS 固定成浅色 | 给窗口补上 `objectName="Root"` 与 `WA_StyledBackground`，让程序自己的主题规则真正生效 |

> 第二个问题的排查过程值得一提：我一度以为是自己的改动把主题弄坏了，
> 于是做了**未打补丁的原版基线对比** —— 结果原版在同一时刻也是深色的。
> 再查注册表 `AppsUseLightTheme = 0`，确认是 **Windows 自动深色模式**在当天
> 傍晚切换了，而程序本来就有这个缺陷。

> **第三版新增**：播放器栏按你的要求重排（左：控制+音量 / 中：封面+信息+进度 / 右：随机+循环）、

### 5. 顺带修掉两个原版隐患

| 问题 | 说明 |
|---|---|
| **worker 信号直连界面槽** | `progress` / `preview` / `job_done` 等信号都是**直连**的，界面槽直接在 worker 线程里跑，从后台线程去改表格模型、进度条、状态栏。Qt 控件不是线程安全的，只要主线程同时也在碰控件树，就会随机 `0xC0000005` 访问违例崩溃。这次为了做进度文字踩了很久，最后定位到：**只要给 `on_progress` 这个槽套任何一层包装（哪怕只是纯转发）就会崩**。最终方案是完全不碰界面槽，改在 `core.scan_folder` / `core.execute_jobs` 的回调里记录进度 |
| **扫描后界面永久忙碌** | 见第二版那一节，仍在生效 |

> 排查过程值得记一笔：我一度用 `QThread.currentThread() is 主线程` 判断线程，
> 但 PySide6 每次返回**新的包装对象**，`is` 比较恒为 False —— 这个错误的判断方式
> 让结论反复摇摆。换成 `threading.get_ident()` 之后才拿到可靠结论。

## ⚠️ 首次运行前必读：为什么双击会报错

**症状**：双击 `iTunes助手.NCM版.exe` 报错；右键「以管理员身份运行」却正常。

**原因**：这个 exe 是在 `D:\新建文件夹\` 里生成的，而该目录被本机的开发沙箱打上了
**低完整性级别（Low Mandatory Level）** 标签，目录里的所有文件都会继承它：

```
> icacls "iTunes助手.NCM版.exe"
  ...
  Mandatory Label\Low Mandatory Level:(I)(NW)      ← 问题在这里
```

Windows 的强制完整性控制（MIC）规则是：

| 场景 | 结果 |
|---|---|
| 双击一个 **Low** 级别的 exe | 进程以 **低完整性** 运行 |
| 低完整性进程往 `%TEMP%` 等 **Medium** 位置写 | **被拒绝**（no-write-up） |
| PyInstaller 单文件程序启动时 | **必须先往 `%TEMP%` 解包出 `_MEI` 目录**（96 MB） |
| → 结果 | 解包失败，程序报错退出 |
| 以管理员运行 | 进程是 **High** 完整性，**降级写入是允许的** → 成功 |

顺带一提：就算解包成功了，低完整性进程依然**没法把整理好的音乐写到桌面、D 盘等位置**，
所以这个标签必须去掉，没有别的绕法。

**解决办法**（只需要做一次）：

运行同目录下的 **`首次运行-安装到桌面.cmd`**。它会：

1. 把 exe 复制到 `%LOCALAPPDATA%\Programs\iTunes助手\`
2. 校验副本的完整性级别
3. 在桌面创建「iTunes 助手」快捷方式
4. 启动程序

**关于「发送到桌面快捷方式」为什么没用**：那只是创建了一个 `.lnk`，指向的仍然是
`D:\新建文件夹\` 里那个带标签的**原件**，所以照样报错。必须是**复制**一份出来。

**为什么这次通常不需要管理员**：标签是**继承**来的（`icacls` 里那个 `(I)`），
而**继承来的 ACE 不会随复制带走** —— 副本会继承目标目录的 Medium 级别，
所以单纯复制一步往往就已经修好了。只有当副本仍显示 `Low`（比如标签被显式写过）
脚本才会请求提权，用 `icacls /setintegritylevel Medium` 修正；整个过程最多弹一次 UAC。

之后直接双击桌面的「iTunes 助手」即可，不需要管理员，也不用再运行脚本，
原来那个带标签的 exe 可以放心删掉。

> **两条快速自检**
> 1. 想看标签：`icacls "路径\iTunes助手.NCM版.exe" | findstr Mandatory`
>    出现 `Low Mandatory Level` 就是这个原因；没有输出或显示 `Medium` 就正常。
> 2. **拿原版 `iTunes助手.exe` 在同一个文件夹里双击，会报一样的错。**
>    这能证明问题出在目录/文件的属性上，与本次功能改动无关。

## 一、先搞清楚这个程序是什么

拿到 38 MB 的 `iTunes助手.exe`，先做技术侦察：

| 项目 | 结论 |
|---|---|
| PE 架构 | x64，GUI 子系统，7 个节区 |
| 节区总大小 | 约 300 KB —— 主体不在 PE 里 |
| 打包方式 | **PyInstaller onefile**，`MEI` 魔数在文件尾 38056055 处 |
| Python 版本 | **3.14**（cookie 里 pyver=314，`python314.dll`） |
| 界面框架 | **PySide6**（Qt 6.12.0） |
| CArchive | 从偏移 `0x4F400` 开始，165 个条目，内含 PYZ（201 个模块） |

把归档解开之后，**应用自身的代码只有 3 个模块**：

| 模块 | 行数规模 | 职责 |
|---|---|---|
| `app.py` | 约 1050 行 | Qt 界面：无边框窗口、侧栏、任务表、Worker 线程 |
| `core.py` | 约 660 行 | 纯逻辑：扫描、读标签、规划目标路径、归档、去重、写播放列表 |
| `theme.py` | 约 210 行 | 深色/浅色 QSS 主题 |

第三方依赖里有个关键角色：**`mutagen`**（音频标签读写库）。也就是说这个程序本来就在
干「读标签 → 按标签重命名 → 归档」这件事。它现在做的事是：

```
扫描源文件夹 → mutagen 读标签 → 按 {artist} - {title} 模板命名
            → 按日期/专辑归档到输出目录 → 批内去重 → 生成 导入 iTunes.m3u8
```

### 缺口在哪里

`core.py` 自己的文档字符串就写明了边界：

> 设计前提：处理的都是本就**无加密保护**的常见音频容器（mp3 / m4a / flac / wav 等）。

`scan_folder()` 的文档更直接：

> 只认 `AUDIO_EXTS` 中的扩展名；其余文件（**包括各类加密容器**）一律忽略并计数，
> **本工具不对它们做任何处理**。

`.ncm` 正是那个「加密容器」。所以这次集成不是硬塞功能，而是补上作者明确留出来的缺口。

## 二、集成方案

### 2.1 注入点：猴补丁 `core.scan_folder`

反汇编 `app.Worker` 可以看到，它调用核心层用的是属性访问：

```
Worker.do_scan  引用名字: ['core', 'scan_folder', 'source', 'recursive', 'log', 'emit', 'progress', 'plan_jobs', ...]
Worker.do_run   引用名字: ['core', 'scan_folder', ..., 'execute_jobs', '_job_done', 'make_playlist', 'write_playlist', ...]
```

`core.scan_folder(...)` 而不是 `from core import scan_folder` —— 这意味着
**替换 `core.scan_folder` 这个模块属性就能生效，完全不用碰已冻结的 `app` 模块**。

### 2.2 为什么在「扫描阶段」解决

扫描之后的每一个环节（命名模板、按专辑分组、批内去重、复制/移动、m3u8 播放列表）
都只认两件事：**一个真实存在的音频文件** + **一份能读出来的标签**。

所以只要在扫描阶段把 `.ncm` 变成「带着完整标签的真实 MP3/FLAC」，
后面**一行代码都不用改**：

```
core.scan_folder（被打补丁）
    ├─ 先按原样扫一遍普通音频
    ├─ 再找 *.ncm
    ├─ 逐个：解密 → 用 mutagen 写标签和封面 → 落到临时缓存区
    └─ 用解出来的真实文件构造 core.Track，混进同一个列表
            ↓
plan_jobs / execute_jobs / write_playlist  ← 完全原封不动
```

细节：

* 缓存目录放在系统临时目录（可用环境变量 `ITUNES_ASSISTANT_NCM_CACHE` 覆盖），
  **不在源目录里**，否则第二次扫描会把解密结果当成新文件重复处理；
* 缓存文件沿用原文件名 + 真实扩展名（`晴天.ncm` → 缓存里的 `晴天.mp3`），
  这样 `{orig}` 令牌和预览表格里显示的名字都符合直觉；
* NCM 里本来被算进「忽略的非音频文件」，处理成功后会把计数扣回去，
  否则日志会显示「忽略 5 个非音频文件」而列表里却多出 5 首歌；
* `execute_jobs` 结束后立即清空缓存，`atexit` 再兜一次；
* **源 `.ncm` 文件永远只读**，不删除、不修改（有测试专门验证）。

### 2.3 界面层的三处改动

1. 侧栏提示补一句：「源文件夹（待整理的音频）**，支持 .ncm**」
2. 启动时在日志面板写明 NCM 支持已启用
3. 支持**把 `.ncm` 文件直接拖进窗口**（原版 `dropEvent` 只认 `is_dir()`）
   —— 仅当拖进来的**全部是** `.ncm` 时才接管，其它情况一律走原逻辑，
   保证不改变原有行为

### 2.4 怎么把补丁装进已经打包好的 exe

不重新打包整个程序，只**替换 PyInstaller 归档里的一个条目**：入口脚本 `smain`。

新入口把 `ncm_core` / `ncm_tags` / `ncm_patch` 三个模块的**源码内嵌**进来，
用 `sys.modules` 注册成真正的模块，因此：

* **不需要往归档里新增任何条目**；
* 模块之间的 `import` 照常工作；
* 改动面 = 1 个条目，其余 164 个字节不动。

（之所以不把三个模块作为新的归档条目加进去，是因为 CArchive 的模块导入路径由
引导器的 C 代码处理，新增条目的行为没有把握；内嵌则 100% 可控。）

## 三、NCM 格式与解密实现

程序里**没有打包任何加密库**（只有 stdlib + mutagen + PySide6），所以
`ncm_core.py` 自带一份纯 Python 的 AES-128-ECB 解密实现。

### 3.1 容器布局（全部小端）

```
偏移  长度        字段
0     8           magic = "CTENFDAM"
8     2           gap
10    4           key_len
      key_len     加密的 RC4 密钥块
      4           meta_len（可为 0）
      meta_len    加密的 JSON 元数据
      4           crc32（各实现都不校验）
      1           image version
      4           cover_frame_len   封面帧总长（含尾部 padding）
      4           cover_len         封面图实际长度
      cover_len   封面图（裸 JPEG/PNG，未加密）
      padding
      到文件尾    音频（流密码加密）
```

> **最容易踩的坑：必须按 `cover_frame_len` 前进，不能按 `cover_len`。**
> 老客户端总是 `cover_frame_len == cover_len`，于是很多解析器把这两个字段
> 合并成一个「5 字节 gap」，在老文件上恰好是对的。但网易云 3.x 会预留更大的
> 封面帧，而且经常出现 `cover_len == 0` 而 `cover_frame_len` 是几千字节的情况——
> 这时少跳的那段 padding 会被当成音频解密，密钥流整体错位，**整个输出变成噪声**。

### 3.2 三段密码学变换

```
① 密钥块：XOR 0x64 → AES-128-ECB 解密(密钥 "hzHRAmso5kInbaxW")
          → 去掉前缀 "neteasecloudmusic"(17B) → 得到流密码密钥材料

② 元数据：XOR 0x63 → 去掉前缀 "163 key(Don't modify):"(22B) → Base64 解码
          → AES-128-ECB 解密(密钥 "#14ljk_!\]&0U<'(") → 去掉 "music:"/"dj:" → JSON

③ 音频：  标准 RC4 的 KSA 得到置换表 S，但 PRGA 被改成了只依赖绝对偏移的形式：
              j  = (off + 1) mod 256
              a  = S[j]
              b  = S[(a + j) mod 256]
              ks = S[(a + b) mod 256]
          正因为只跟 off 有关，密钥流以 256 为周期，可以摊成一张表反复用。
```

第 ③ 步是 NCM 相对标准 RC4 的「魔改」之处：**状态不演化**，所以能随便分块、
随机 seek 地解密。网上 ncm2mp3.com 的实现用的就是「摊成 256 字节表 + `& 255`」这一招。

### 3.3 性能

| 项目 | 结果 |
|---|---|
| 50 MB 音频的密钥流异或 | **0.26 秒**（约 190 MB/s） |
| AES 解密 | 每首歌只解两小段（几十字节），可忽略 |

实现上用大整数异或（`int.from_bytes(...) ^ int.from_bytes(...)`）跑 C 层循环，
比逐字节 Python 循环快一个数量级。

### 3.4 标签与封面

复用程序里已有的 mutagen：

| 格式 | 文本标签 | 封面 |
|---|---|---|
| MP3 | ID3v2.3 的 TIT2/TPE1/TALB/TRCK（UTF-16 + BOM，中文安全） | APIC 帧 |
| FLAC | Vorbis Comment | PICTURE 元数据块 |
| M4A | `©ART`/`©nam`/`©alb`/`trkn` | `covr` |
| OGG/Opus | Vorbis Comment | — |

任何一步失败都**静默退化为「无标签」**，绝不因为写标签失败而中断整批任务
（与 `core.read_metadata` 的既有约定一致）。FLAC 只插入元数据块，**音频帧逐字节不动**。

## 六、验证体系

改动一个已打包的商业程序，光「看起来对」是不够的。这里做了四层互相独立的验证，
全部由 `run_all_tests.py` 一键复现。

### 第 1 层：NCM 解码核心（26 项）

| 验证 | 依据 |
|---|---|
| AES-128-ECB 解密 | **Node/OpenSSL 生成的 51 条测试向量** + FIPS-197 标准向量 |
| S 盒构造 | 自检 `SBOX[0] == 0x63` 且逆置换自洽 |
| 密钥流周期表 | 与**照规范逐偏移计算、不打表**的参考实现比对（30 组随机密钥 × 256 偏移） |

> 这里刻意避免了循环论证：AES 用 OpenSSL 当裁判，密钥流用独立参考实现当裁判，
> 容器解析用上一轮已经被网站自己的 `decrypt.js` 验证过的样本当裁判。

### 第 2 层：端到端集成（40 项）

- 原生 mp3 的字节完全没被碰过；

实例化真实的 `MainWindow` 后检查：

### 第 4 层：归档结构与真实运行（15 项 + 冒烟）

## 七、已知限制

1. **产物 exe 必须先做一次「去低完整性标签」处理，否则双击会报错。**
   这就是开头那一节讲的问题，根因已经查清并确认：

   * 本机的开发沙箱运行在**低完整性**下，因此它把唯一可写的目录 `D:\新建文件夹`
     整个标记成了 `Mandatory Label\Low Mandatory Level`，里面生成的文件都继承该标签；
   * 带该标签的 exe 双击后进程也是低完整性，无法往 `%TEMP%` 解包 `_MEI`，
     于是 PyInstaller 启动失败；以管理员运行 = 高完整性，可以降级写入，所以正常；
   * 实测排除了其它可能：PE 清单是 `asInvoker`（与原版逐字节相同）、无数字签名、
     程序自身不使用 `winreg`/HKLM、没有任何硬编码的受保护路径。

   因为这属于「文件所在目录的权限属性」，沙箱内的进程无权修改
   （`icacls /setintegritylevel` 返回 `Access is denied`，需要 `SeRelabelPrivilege`），
   所以做成了 `首次运行-安装到桌面.cmd` 让用户侧一次性完成。

   替代验证做到了什么程度：把归档重建之后**逐字节确认只动了入口脚本这一个条目**，
   再用本机 Python 3.14 以 `__main__` 身份**实际执行了被编译进 exe 的同一个
   code object**，跑通了完整的解密→打标签→归档链路并截了图。

   修好权限后，验证只要一步：双击 exe，看侧栏是否显示「支持 .ncm」。

2. **`action = 移动` 时只移动解密结果，源 `.ncm` 会保留。**
   这是有意为之——不应该悄悄删掉用户的原始文件。

3. **封面原样嵌入，不做压缩。**
   如果某些 NCM 里塞了特别大的封面（>1 MB），输出文件的标签部分会相应变大。
   （ncm2mp3.com 会把大图缩到一半再压成 JPEG，代价是有损。）

4. **需要 `%TEMP%` 可写。** 不可写时会自动降级到用户主目录，
   也可以用 `ITUNES_ASSISTANT_NCM_CACHE` 显式指定。

## 九、一点说明

NCM 的加密密钥是 2016 年起就公开的硬编码常量，本方案没有做任何绕过账号、
破解付费内容的事情——它做的事和 ncm2mp3.com 一样：**把你自己已经下载到本地的文件
去掉一层容器壳**，让它们能进 iTunes。音频数据一个比特都没有重新编码。

请只用于自己合法获取的音乐，不要用于传播或再分发。
